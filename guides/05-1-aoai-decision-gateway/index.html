0. TL;DR

Decision-1은 글을 생성하지 않고, 텍스트나 JSON에 대해 타입이 있는 숫자 결정(확률·선택지·점수)을 돌려주는 모델입니다. 이 특성을 LLM 앞단 게이트웨이로 쓰면, 요청마다 의도·리스크·난이도·도구를 먼저 한 번에 판단하고 필요한 요청만 알맞은 LLM·도구 조합으로 보낼 수 있습니다.

질문답
LLM을 부르기 전에 무엇을 하나?Decision-1을 1회 호출해 의도·리스크·난이도·tool_loadout을 한꺼번에 판단합니다. 질문 여러 개를 한 요청에 담을 수 있습니다.
모델과 도구는 언제 정하나?정책 게이트를 통과한 뒤 라우팅 테이블 조회로 정합니다. 추가 모델 호출은 없고, LLM은 그 선택이 끝난 뒤 1회 호출합니다.
Model Router(05)와는 어떻게 다른가?Model Router가 요청별 모델 선택을 맡는다면, 이 가이드는 그 앞단의 판단·도구 선택·정책 검증을 다룹니다. 둘을 함께 구성할 수도 있습니다.
비용·지연이 얼마나 줄어드나?설계 의도이며 워크로드별로 측정해야 합니다. 이 문서의 수치는 예시이고 보장 값이 아닙니다.

최소 도입 순서

  1. 대표 요청과 정답 라벨을 모아 평가 세트를 만듭니다.
  2. Foundry 모델 카탈로그에서 Microsoft-Decision-1을 배포하고, 판단할 질문(의도·난이도·위험·도구)을 설계합니다.
  3. 평가 세트로 오분류·미분류 비용을 따져 확률 임계치를 정합니다.
  4. 판단 라벨을 모델 등급·도구 묶음에 매핑하는 라우팅 테이블을 작성합니다.
  5. 섀도 모드로 선택 경로(selected)와 실제 경로(executed)를 비교하며 검증한 뒤 점진적으로 전환합니다.

1. 왜 Decision 게이트웨이인가

모든 요청을 가장 큰 모델과 모든 도구로 처리하면 단순한 요청에도 추론 비용, 긴 컨텍스트, 넓은 실행 권한이 따라옵니다. 게이트웨이는 LLM을 부르기 전에 이를 걸러냅니다.

  • 비용·지연 — 저난도 요청은 효율 모델로, 고난도 요청만 추론 모델로 보냅니다.
  • 오동작·보안 면적 — 선택된 도구 스키마만 프롬프트에 넣어, 모든 도구를 노출하지 않습니다.
  • 예측 가능성 — 확률이 있는 결정이라 임계치로 자동 실행·재평가·사람 검토를 가를 수 있습니다.

질문 유형

Decision-1은 state(텍스트 또는 JSON)와 하나 이상의 타입 있는 질문을 받습니다. 응답의 answers는 요청에서 붙인 질문 이름을 그대로 씁니다.

질문타입결과게이트웨이에서의 용도
참인가?noul0~1 확률프롬프트 인젝션 여부, 프로덕션 데이터 접근 여부 같은 게이트·필터
어떤 선택지인가?choice선택된 옵션 + 옵션별 확률의도 분류, tool_loadout 선택, 팀 라우팅
얼마나 되는가?score순서 척도 값 + 레벨별 확률난이도·심각도처럼 순위·임계치가 필요한 판단

Microsoft Learn은 활용 사례로 게이트·필터, 분류·라우팅, 우선순위, 평가, 그리고 요청을 처리할 모델·도구·에이전트 선택을 듭니다. 새로 글을 쓰거나 요약·설명해야 하면 생성형 LLM을 쓰고, Decision-1은 그 앞에서 라우팅·게이팅을 맡는 조합을 권장합니다.

2. 전체 아키텍처

  • Decision-1은 질문 1회 호출로 라벨(의도·리스크·난이도·도구)을 만듭니다.
  • 정책 게이트는 확률 임계치와 허용 목록으로 통과·되묻기·사람 검토를 가릅니다.
  • 라우팅 테이블은 라벨을 모델 등급과 도구 묶음에 단순 매핑합니다. 여기서는 모델을 다시 부르지 않습니다.
  • LLM은 선택이 끝난 뒤 1회 호출하고, 결과는 품질 게이트와 관측을 거칩니다.

3. 동작 흐름: 판단 → 적용 → 실행 → 검증

3.1 판단 (Decision-1 1회 호출 + 정책 게이트)

한 줄 요약 — Decision-1을 1회 호출해 의도·리스크·난이도·도구를 한 번에 판단하고, 정책 게이트를 통과한 요청만 다음 단계로 보냅니다(아직 LLM 호출 없음).

요청을 그대로 실행하지 않고 choice·score·noul 질문을 한 번에 담아 호출합니다. 결과는 정책 게이트(확률 임계치·허용 목록)로 검증하고, 이 경계까지가 '판단'입니다. 통과한 요청은 판단 라벨을 달고 다음 단계로 넘어갑니다.

3.2 적용 (라우팅 테이블 + LLM 호출)

한 줄 요약 — 판단 결과를 라우팅 테이블로 모델 등급·도구에 매핑(추가 모델 호출 없음)한 뒤, 선택된 조합으로 LLM을 1회 호출합니다.

난이도는 모델 등급에, tool_loadout은 도구 묶음에 그대로 대응시키는 단순 조회입니다. 그래서 Decision-1을 다시 부르지 않습니다. LLM 프롬프트에는 선택된 도구 스키마만 넣어 컨텍스트 오염과 오동작 면적을 줄입니다.

3.3 실행·검증 (품질 게이트 + 관측)

한 줄 요약 — 실패 시 1회만 승격하고 selected/executed route·지연·비용을 기록해 지속적으로 튜닝합니다.

선택 경로(selected)와 실제 경로(executed)를 분리해 기록하면, 게이트가 막은 요청과 승격된 요청을 나중에 분석할 수 있습니다. 임계치와 라우팅 테이블은 이 지표로 주기적으로 다시 조정합니다.

3.4 구간 경계 한눈에 보기

구간하는 일모델 호출LLM 호출
판단질문 1회로 라벨 생성 + 정책 게이트 검증Decision-1 1회아직 없음
적용라벨을 모델 등급·도구에 매핑(조회)없음선택 후 1회 호출
검증품질 게이트, 실패 시 1회 승격, 관측 기록실패 시 상위 모델 1회승격 시에만 추가

경계는 정책 게이트입니다. 게이트 앞은 '판단', 뒤는 '적용과 실행'입니다.

4. 적용 워크로드 (우선순위 순)

아래는 효과를 기대할 수 있는 순서입니다. 효과는 설계 의도이며 실제 워크로드로 측정해 검증해야 합니다.

우선순위 · 워크로드Decision-1이 판단하는 것기대 효과확인할 점
1. 난이도 기반 모델 라우팅choice(low/high)로 난이도 → 모델 등급저난도는 효율 모델, 고난도만 추론 모델로 보내 단가와 지연 관리난이도 임계치를 평가 세트로 검증
2. 대량 티켓 분류choice로 팀·의도 + 옵션별 확률확률이 낮은 건만 LLM·상담원으로 보내 평균 응답시간과 토큰 감소임계치와 오분류 비용, 기권 옵션(예: cannot_tell)
3. 에이전트 액션 게이트noul·choice로 위험도·권한승인된 액션만 실행해 롤백·재시도·장애 대응 비용 감소선택과 실행 권한을 분리하고, 중대한 결정은 사람 검토
4. 문서·요약 생성choice로 문서 유형·스타일·템플릿생성은 OpenAI 등 LLM에 맡기고 앞단 분류·정책만 Decision이 담당생성 품질은 별도 평가로 확인
5. 하이브리드 운영위 판단 라벨 전체 + 실행 로그selected/executed route·fallback율·지연·비용을 추적해 정책 튜닝 속도와 비용 예측 정확도 향상지표 정의와 알림 기준

5. Decision-1 호출·응답·정책 설계

이 장은 Microsoft-Decision-1의 Microsoft Learn 문서와, Decision-1을 실제 배포에 호출해 검증한 Microsoft-Decision-workshop 코드(2026-10-12 검증)를 근거로 합니다. 문서와 코드에서 확인되지 않은 응답 필드는 쓰지 않았습니다.

5.1 요청 만들기

엔드포인트는 Foundry 리소스의 /providers/microsoft/v1/systemone입니다. 요청의 model에는 모델 이름이 아니라 배포 이름을 넣고, 판단할 내용은 state(텍스트 또는 JSON)에, 판단 항목은 questions에 타입이 있는 질문으로 담습니다. 같은 state를 보는 질문은 한 요청에 함께 담을 수 있어 호출 수가 줄고 판단 맥락이 일관됩니다.

질문 유형필드결과 (Learn 문서 기준)
choiceinstructions, criteria(옵션 이름 → 설명)선택된 옵션 1개와 옵션별 확률
noulinstructions, criteria(선택, true/false 조건)0~1 확률
scoreinstructions, criteria(낮음→높음 순 레벨 배열)순서 척도의 값과 레벨별 확률 (확률 가중 평균이라 레벨 사이 값 가능)

게이트웨이에서는 choice를 기본으로 쓰는 것을 권장합니다. 난이도처럼 순서가 있는 판단도 low/high 같은 옵션 두 개로 표현할 수 있습니다.

POST <your-foundry-resource-endpoint>/providers/microsoft/v1/systemone
Content-Type: application/json
Authorization: Bearer <entra-access-token>

{
  "model": "<deployment-name>",
  "state": "Please delete the stale rows in the orders table.",
  "questions": {
    "complexity": {
      "type": "choice",
      "instructions": "How hard is this request to complete correctly?",
      "criteria": {
        "low": "Lookup, tagging, short rewrite, or a single simple step",
        "high": "Multi-step analysis, planning, or reasoning across sources"
      }
    },
    "tool_loadout": {
      "type": "choice",
      "instructions": "Select the minimum tool set needed. Select answer_only when no tool is needed.",
      "criteria": {
        "answer_only": "No tools needed",
        "inspect": "Read-only tools",
        "edit": "Read and edit tools",
        "shell": "Read, edit, and shell tools"
      }
    }
  }
}

인증 — Microsoft Entra ID Bearer 토큰(권장, 스코프 https://cognitiveservices.azure.com/.default) 또는 api-key 헤더를 씁니다.

옵션 설계 — 옵션 설명은 서로 겹치지 않게 쓰고, 해당 없음을 위한 기권 옵션(answer_only, none, cannot_tell 등)을 두세요. 워크샵의 도구 선택은 "관련 도구가 없으면 none"을 옵션으로 둡니다.

5.2 응답 읽기

응답의 answers는 요청에서 붙인 질문 이름을 키로 씁니다. choice 질문은 type, 선택된 옵션 choice, 옵션별 확률 probabilities를 돌려줍니다. 이 필드들은 워크샵 코드가 실제 배포 응답에서 읽는 값입니다. 응답에는 배포된 모델 이름과 토큰 사용량도 함께 들어 있습니다.

{
  "model": "microsoft-decision-1",
  "answers": {
    "complexity": {
      "type": "choice",
      "choice": "low",
      "probabilities": { "low": 0.97, "high": 0.03 }
    },
    "tool_loadout": {
      "type": "choice",
      "choice": "edit",
      "probabilities": { "answer_only": 0.02, "inspect": 0.15, "edit": 0.78, "shell": 0.05 }
    }
  }
}

위 예시의 확률 값은 형태를 보여 주기 위한 임의의 숫자입니다. 선택된 옵션의 확률은 probabilities[choice]로 읽습니다.

5.3 정책 게이트와 라우팅 테이블

판단 결과를 정책으로 옮깁니다. 게이트는 선택된 옵션의 확률이 임계치 미만이거나 기권 옵션이 선택되면 요청을 멈추고, 통과한 요청만 라우팅 테이블로 모델 등급과 도구를 정합니다. Learn 문서는 낮은 상위 확률을 사람이나 다른 모델에 넘기는 신호로 쓰라고 안내합니다. 아래 값은 예시이며, 워크샵은 라우팅·도구 선택에 0.60을 썼습니다. 임계치는 평가 세트에서 오분류·미분류 비용을 따져 정하세요.

{
  "gate": {
    "min_top_probability": 0.60,
    "on_low_probability": "clarify_or_human_review",
    "on_none": "answer_without_tools"
  },
  "route_table": {
    "model_tier": { "low": "efficient", "high": "reasoning" },
    "tool_loadout": {
      "answer_only": [],
      "inspect": ["read_file", "search"],
      "edit": ["read_file", "search", "edit_file"],
      "shell": ["read_file", "search", "edit_file", "run_shell"]
    }
  },
  "escalation": { "max_upgrades": 1 }
}

선택(selected)과 실행(executed)을 분리해 기록하세요. 워크샵 코드도 선택된 경로와 실제 실행된 경로(예: 확률 미달 시 fallback)를 따로 남겨서, 게이트가 막은 요청을 나중에 분석할 수 있습니다.

5.4 최소 구현 예시

아래는 위 설계를 한 함수로 옮긴 축약 예시입니다. 요청 형태와 choice 응답 파싱은 Learn 문서와 워크샵 클라이언트(decision_client.py)와 같은 방식이며, 임계치와 라우팅 테이블 값은 예시입니다. 반환값의 tools와 모델 등급으로 LLM을 1회 호출하는 부분은 각자의 코드로 연결합니다.

import json
import os
import urllib.error
import urllib.request

from azure.identity import DefaultAzureCredential

ENDPOINT = os.environ["AZURE_ENDPOINT"].rstrip("/")
DEPLOYMENT = os.environ["DEPLOYMENT_NAME"]
SCOPE = "https://cognitiveservices.azure.com/.default"
MIN_PROBABILITY = 0.60  # example: tune on a labeled evaluation set

QUESTIONS = {
    "complexity": {
        "type": "choice",
        "instructions": "How hard is this request to complete correctly?",
        "criteria": {"low": "Simple, single step", "high": "Multi-step reasoning"},
    },
    "tool_loadout": {
        "type": "choice",
        "instructions": "Select the minimum tool set needed.",
        "criteria": {
            "answer_only": "No tools needed",
            "inspect": "Read-only tools",
            "edit": "Read and edit tools",
        },
    },
}
MODEL_TIER = {"low": "efficient", "high": "reasoning"}
TOOLS = {"answer_only": [], "inspect": ["read_file"], "edit": ["read_file", "edit_file"]}


def decide(request: str) -> dict:
    token = DefaultAzureCredential().get_token(SCOPE).token
    body = json.dumps({"model": DEPLOYMENT, "state": request, "questions": QUESTIONS}).encode()
    req = urllib.request.Request(
        f"{ENDPOINT}/providers/microsoft/v1/systemone",
        data=body,
        method="POST",
        headers={"Content-Type": "application/json", "Authorization": f"Bearer {token}"},
    )
    try:
        with urllib.request.urlopen(req, timeout=60) as resp:
            answers = json.loads(resp.read())["answers"]
    except urllib.error.HTTPError as exc:
        raise RuntimeError(f"Decision API returned HTTP {exc.code}") from exc

    picked = {}
    for name, question in QUESTIONS.items():
        answer = answers[name]
        choice = answer["choice"]
        if choice not in question["criteria"]:
            raise RuntimeError(f"unexpected choice {choice!r} for {name}")
        picked[name] = (choice, float(answer["probabilities"][choice]))
    return picked


def route(request: str) -> dict:
    picked = decide(request)
    # the gate runs before any lookup: one low-probability answer stops the request
    if any(prob < MIN_PROBABILITY for _, prob in picked.values()):
        return {"selected": picked, "executed": "fallback", "action": "clarify_or_human_review"}
    tier = MODEL_TIER[picked["complexity"][0]]
    tools = TOOLS[picked["tool_loadout"][0]]
    return {"selected": picked, "executed": tier, "tools": tools}  # call the LLM once with these

  • 모델이 억지로 고르지 않도록 cannot_tell 같은 기권 옵션을 둡니다.
  • 질문·옵션 문구는 명확하고 중립적으로 쓰고, 옵션 순서를 바꿔 결과가 흔들리는지 테스트합니다.
  • top 확률이 낮으면 사람 또는 다른 모델로 넘기는 에스컬레이션 경로를 둡니다.

  • 저신뢰·오류 시 안전한 기본 경로(추론 경로 또는 안전 응답)를 정의합니다.
  • 신용·고용·주거·의료·법률처럼 개인에 대한 중대한 결정은 단독 결정자로 쓰지 말고 사람 검토를 둡니다.
  • 섀도 모드로 먼저 돌려 기존 경로와 결과를 비교한 뒤 점진적으로 전환합니다.

0. TL;DR

Decision-1 does not generate prose; it returns typed numerical decisions (probabilities, selected options, scores) about text or JSON. Used as a gateway in front of LLMs, it judges intent, risk, complexity, and tools in one pass, so only the requests that need it reach the right LLM and tool combination.

QuestionAnswer
What happens before the LLM call?One single Decision-1 call judges intent, risk, complexity, and tool_loadout together. Several questions can share one request.
When are model and tools chosen?After the policy gate, through a route table lookup. There is no extra model call, and the LLM is called once after the selection.
How does it differ from Model Router (05)?If Model Router handles per-request model selection, this guide covers the judgment, tool selection, and policy checks in front of it. The two can be combined.
How much cost and latency is saved?It is a design intent that must be measured per workload. Numbers in this document are examples, not guarantees.

Minimum adoption path

  1. Collect representative requests with expected labels as an evaluation set.
  2. Deploy Microsoft-Decision-1 from the Foundry model catalog and design the questions (intent, complexity, risk, tools).
  3. Set probability thresholds from your evaluation set, weighing the cost of false positives and false negatives.
  4. Write a route table that maps decision labels to model tiers and tool sets.
  5. Validate in shadow mode, comparing selected and executed routes, then switch over gradually.

1. Why a Decision gateway

Sending every request to the largest model with every tool attached brings reasoning cost, long context, and broad execution rights even to trivial requests. A gateway filters this before the LLM is called.

  • Cost and latency — Route low-complexity requests to efficient models and only hard ones to reasoning models.
  • Execution and security surface — Inject only the selected tool schemas instead of exposing every tool.
  • Predictability — Probabilistic decisions let thresholds separate automatic action, re-evaluation, and human review.

Question types

Decision-1 accepts a state (text or JSON) and one or more typed questions. The answers object in the response uses the question names from your request.

QuestionTypeResultUse in a gateway
Is this true?noulProbability from 0 to 1Gates and filters such as prompt injection or production data access
Which option is it?choiceSelected option plus probability per optionIntent classification, tool_loadout selection, team routing
How much?scoreValue on an ordered scale plus probability per levelComplexity or severity where ranking and thresholds matter

Microsoft Learn lists gates and filters, classification and routing, ranking, grading, and selecting the model, tool, or agent for a request as use cases. When content must be written, summarized, or explained, use a generative LLM and let Decision-1 route or gate in front of it.

2. Architecture

  • Decision-1 produces labels (intent, risk, complexity, tools) in a single call.
  • The policy gate uses probability thresholds and allowlists to pass, clarify, or send to human review.
  • The route table maps labels to a model tier and tool set. No model is called again here.
  • The LLM is called once after the selection, and the result goes through the quality gate and telemetry.

3. Flow: decide → apply → execute → verify

3.1 Decide (one Decision-1 call + policy gate)

In one line — One Decision-1 call judges intent, risk, complexity, and tools together, and only requests that pass the policy gate move on (no LLM call yet).

Instead of executing the request as-is, send choice, score, and noul questions in one call. The result is validated by the policy gate (probability threshold, allowlist); this boundary ends the 'decide' step. Approved requests carry their decision labels to the next step.

3.2 Apply (route table + LLM call)

In one line — A route table maps the decision labels to a model tier and tools (no extra model call), then the LLM is called once with that selection.

Complexity maps to a model tier and tool_loadout maps to a tool set, so this is a plain lookup and Decision-1 is not called again. Only the selected tool schemas go into the LLM prompt, reducing context bloat and execution risk.

3.3 Execute and verify (quality gate + telemetry)

In one line — Escalate once on failure and record selected/executed route, latency, and cost to keep tuning.

Recording the selected route separately from the executed route lets you analyze requests the gate blocked and requests that were escalated. Re-tune thresholds and the route table from these metrics on a regular basis.

3.4 Boundaries at a glance

StageWhat it doesModel callsLLM call
DecideCreate labels with one question call and validate with the policy gateDecision-1 onceNot yet
ApplyMap labels to model tier and tools (lookup)NoneOnce, after selection
VerifyQuality gate, one escalation on failure, telemetryOne stronger model on failureOnly on escalation

The boundary is the policy gate: before it is 'decide', after it is 'apply and execute'.

5. Decision-1 calls, responses, and policy design

This chapter is grounded in the Microsoft Learn article for Microsoft-Decision-1 and in the Microsoft-Decision-workshop code, which calls a live Decision-1 deployment (validated 2026-10-12). Response fields that neither source confirms are not used.

5.1 Building the request

The endpoint is /providers/microsoft/v1/systemone on your Foundry resource. Set model to your deployment name, not the model name, put the content to judge in state (text or JSON), and describe each judgment as a typed entry in questions. Questions about the same state can share one request, which reduces calls and keeps the decision context consistent.

Question typeFieldsResult (per the Learn article)
choiceinstructions, criteria (option name → description)One selected option and a probability for each option
noulinstructions, optional criteria (true/false conditions)A probability from 0 through 1
scoreinstructions, criteria (levels listed lowest to highest)A value on an ordered scale and a probability for each level (a probability-weighted average, so it can fall between levels)

For a gateway, prefer choice questions. Ordered judgments such as complexity can be expressed as two options like low/high.

POST <your-foundry-resource-endpoint>/providers/microsoft/v1/systemone
Content-Type: application/json
Authorization: Bearer <entra-access-token>

{
  "model": "<deployment-name>",
  "state": "Please delete the stale rows in the orders table.",
  "questions": {
    "complexity": {
      "type": "choice",
      "instructions": "How hard is this request to complete correctly?",
      "criteria": {
        "low": "Lookup, tagging, short rewrite, or a single simple step",
        "high": "Multi-step analysis, planning, or reasoning across sources"
      }
    },
    "tool_loadout": {
      "type": "choice",
      "instructions": "Select the minimum tool set needed. Select answer_only when no tool is needed.",
      "criteria": {
        "answer_only": "No tools needed",
        "inspect": "Read-only tools",
        "edit": "Read and edit tools",
        "shell": "Read, edit, and shell tools"
      }
    }
  }
}

Authentication — Use a Microsoft Entra ID bearer token (recommended; scope https://cognitiveservices.azure.com/.default) or an api-key header.

Option design — Keep option descriptions distinct and include an abstain option for non-applicable cases (answer_only, none, cannot_tell). The workshop's tool selector offers none for "no relevant tool".

5.2 Reading the response

The answers object is keyed by the question names from your request. A choice question returns type, the selected option in choice, and per-option probabilities in probabilities. These are the fields the workshop code reads from live deployment responses. The response also includes the deployed model name and token usage.

{
  "model": "microsoft-decision-1",
  "answers": {
    "complexity": {
      "type": "choice",
      "choice": "low",
      "probabilities": { "low": 0.97, "high": 0.03 }
    },
    "tool_loadout": {
      "type": "choice",
      "choice": "edit",
      "probabilities": { "answer_only": 0.02, "inspect": 0.15, "edit": 0.78, "shell": 0.05 }
    }
  }
}

The probabilities above are arbitrary numbers that only show the shape. Read the selected option's probability as probabilities[choice].

5.3 Policy gate and route table

Move the decision into policy. The gate stops a request when the selected option's probability is below the threshold or an abstain option is selected, and only passing requests go through the route table to a model tier and tools. The Learn article recommends using a low top probability as a signal to escalate to a person or another model. The values below are examples; the workshop used 0.60 for routing and tool selection. Set thresholds from your evaluation set by weighing the cost of false positives and false negatives.

{
  "gate": {
    "min_top_probability": 0.60,
    "on_low_probability": "clarify_or_human_review",
    "on_none": "answer_without_tools"
  },
  "route_table": {
    "model_tier": { "low": "efficient", "high": "reasoning" },
    "tool_loadout": {
      "answer_only": [],
      "inspect": ["read_file", "search"],
      "edit": ["read_file", "search", "edit_file"],
      "shell": ["read_file", "search", "edit_file", "run_shell"]
    }
  },
  "escalation": { "max_upgrades": 1 }
}

Record selected and executed separately. The workshop code also keeps the selected route apart from the route actually executed (for example fallback when the probability is too low), so requests the gate blocked can be analyzed later.

5.4 Minimal implementation

The code below turns the design above into one function as a condensed example. The request shape and choice parsing follow the Learn article and the workshop client (decision_client.py); the threshold and route table values are examples. Wire the returned model tier and tools into your own code to call the LLM once.

import json
import os
import urllib.error
import urllib.request

from azure.identity import DefaultAzureCredential

ENDPOINT = os.environ["AZURE_ENDPOINT"].rstrip("/")
DEPLOYMENT = os.environ["DEPLOYMENT_NAME"]
SCOPE = "https://cognitiveservices.azure.com/.default"
MIN_PROBABILITY = 0.60  # example: tune on a labeled evaluation set

QUESTIONS = {
    "complexity": {
        "type": "choice",
        "instructions": "How hard is this request to complete correctly?",
        "criteria": {"low": "Simple, single step", "high": "Multi-step reasoning"},
    },
    "tool_loadout": {
        "type": "choice",
        "instructions": "Select the minimum tool set needed.",
        "criteria": {
            "answer_only": "No tools needed",
            "inspect": "Read-only tools",
            "edit": "Read and edit tools",
        },
    },
}
MODEL_TIER = {"low": "efficient", "high": "reasoning"}
TOOLS = {"answer_only": [], "inspect": ["read_file"], "edit": ["read_file", "edit_file"]}


def decide(request: str) -> dict:
    token = DefaultAzureCredential().get_token(SCOPE).token
    body = json.dumps({"model": DEPLOYMENT, "state": request, "questions": QUESTIONS}).encode()
    req = urllib.request.Request(
        f"{ENDPOINT}/providers/microsoft/v1/systemone",
        data=body,
        method="POST",
        headers={"Content-Type": "application/json", "Authorization": f"Bearer {token}"},
    )
    try:
        with urllib.request.urlopen(req, timeout=60) as resp:
            answers = json.loads(resp.read())["answers"]
    except urllib.error.HTTPError as exc:
        raise RuntimeError(f"Decision API returned HTTP {exc.code}") from exc

    picked = {}
    for name, question in QUESTIONS.items():
        answer = answers[name]
        choice = answer["choice"]
        if choice not in question["criteria"]:
            raise RuntimeError(f"unexpected choice {choice!r} for {name}")
        picked[name] = (choice, float(answer["probabilities"][choice]))
    return picked


def route(request: str) -> dict:
    picked = decide(request)
    # the gate runs before any lookup: one low-probability answer stops the request
    if any(prob < MIN_PROBABILITY for _, prob in picked.values()):
        return {"selected": picked, "executed": "fallback", "action": "clarify_or_human_review"}
    tier = MODEL_TIER[picked["complexity"][0]]
    tools = TOOLS[picked["tool_loadout"][0]]
    return {"selected": picked, "executed": tier, "tools": tools}  # call the LLM once with these

5.5 Call errors and retries

HTTP statusPossible causeAction
400Invalid question type or request shapeCheck state, questions, type, and criteria
401 / 403Missing, invalid, or expired credential, or no access to the deploymentRefresh the token and verify the role assignment and deployment access
404Incorrect resource endpoint or API pathVerify the endpoint on the deployment details page
422Unsupported deployment name or question definitionVerify the model value and each question definition
429Deployment rate limit exceededRetry with exponential backoff or request more quota

The gateway should fail safe when a call fails. If the Decision-1 call fails, do not pass the request straight to an LLM; route it to a safe default path (the reasoning route or a safe response), or retry and then hand it to human review. When parsing, always verify that the returned option is one of the options your request defined.

7. Operations and validation checklist

  • Validate questions and options on representative data, then set thresholds based on the cost difference between false positives and false negatives.
  • Add an abstain option such as cannot_tell so the model is not forced to choose.
  • Keep question and option wording clear and neutral, and test whether reordering options changes results.
  • Provide an escalation path to a person or another model when the top probability is low.
  • Log selected/executed route, fallback rate, latency, and cost per request and re-tune policy regularly.
  • Define a safe default path (reasoning route or a safe response) for low confidence or errors.
  • For consequential decisions about people, such as credit, employment, housing, healthcare, or legal matters, do not use the model as the sole decision-maker; keep human review.
  • Run in shadow mode first, compare against the existing path, then switch over gradually.

8. Limitations and cautions

  • Fairness — The model might reflect biases from its base model and training data. Do not use its scores as the sole basis for decisions about individuals.
  • Wording sensitivity — Scores can change with how questions and options are phrased or ordered, and poorly framed questions still return scores.
  • Reliability — Calibration is strongest on familiar task types; the model provides no explanations and might rely on outdated knowledge.
  • Harmful content — As a safety filter it might miss subtle harmful content or flag benign content.
  • Jev image mode — The API has it, but it needs a vision-language model. Confirm availability on your account first.
  • No guaranteed savings — Cost and latency gains depend on the workload. Prices can change, so check the pricing pages before adopting.
