## 1. 먼저 이해할 3가지 (여기서 대부분 틀립니다)

### ① Global 배포라도 **엔드포인트는 리전 고정**

| 계층 | Global 배포 |
|---|---|
| 추론 처리 | 전 세계 가용 DC로 동적 라우팅 ✅ |
| **리소스 엔드포인트** | `https://<resource>.openai.azure.com` — **리소스 생성 리전에 고정** ❌ |

> *"**Foundry is a regional service**"* · *"**Foundry itself doesn't provide automatic failover or disaster recovery.**"*

**글로벌 라우팅은 "용량 가용성"을 높이지 "엔드포인트 가용성"을 높이지 않습니다.**

### ② 세 가지 이중화는 **서로 다른 계층**을 담당

| 무엇을 이중화하나 | Global 배포 | Spillover | **다중 리소스 + 게이트웨이** |
|---|---|---|---|
| 처리 용량 | ✅ | ✅ | ✅ |
| 배포(용량 풀) | ❌ | ✅ | ✅ |
| **엔드포인트** | ❌ | ❌ | ✅ |

하나로 나머지를 대체할 수 없습니다.

### ③ **쿼터(Quota) ≠ 용량(Capacity)**

- 쿼터는 **정책 한도**(비용 없음), 용량은 **실물 자원**
- **쿼터가 있어도 용량이 없으면 배포 자체가 실패**합니다
- ⚠️ 축소한 PTU 용량은 **다시 확보하지 못할 수 있습니다** → 야간 축소 운영 금지

## 2. 장애 유형별 대응 (오진 방지)

| 유형 | 증상 | 유효한 대응 | **무효한 대응** |
|---|---|---|---|
| **F1** 용량 포화 | 429 | Spillover, 증설 | 재시도 반복(악화) |
| **F2** 서비스 오류 | 500/503 | 재시도 + 다른 배포 | 용량 증설 |
| **F3** 리전(엔드포인트) 장애 | 전체 실패 | **다른 리소스로 Failover** | **Spillover(무력)** |
| **F4** 클라이언트 단절 | 499 | 스트리밍, 타임아웃 정합성 | 리전 Failover |
| **F5** 모델 수명주기 | 400/404 | 버전 고정·마이그레이션 | 인프라 이중화 |
| **F6** 요청 한계 초과 | 400 | Spillover, 프롬프트 압축 | **PTU 증설(무의미)** |

## 3. 배포 유형 선택

### PTU는 세 가지입니다

| 유형 | SKU | 처리 위치 | 최소 PTU | 증분 | Spillover 권장 |
|---|---|---|---|---|---|
| **Global Provisioned** | `GlobalProvisionedManaged` | 전 세계 | **15** | **5** | ✅ |
| **Data Zone Provisioned** | `DataZoneProvisionedManaged` | **US / EU만** (⚠️ APAC 미지원) | **15** | **5** | ✅ |
| **Regional Provisioned** | `ProvisionedManaged` | 단일 리전 | **25~50** | **25~50** | ⚠️ 권장 목록 제외 |

> 💰 Regional은 최소 PTU가 크고 **리전마다 별도 예약**이 필요해, 다중 리전 HA 비용이 급증합니다.

> 🚨 **APAC에는 Data Zone Provisioned가 없습니다.** 개념 문서 일부가 "US/EU/APAC"이라 표기하지만, **모델 리전 가용성 표의 APAC 탭은 "Not available"** 입니다. 배포 유형 × 리전 가용성은 **반드시 가용성 표로 확인**하세요.

### 🇰🇷 한국(Korea Central) 의사결정표

| 요건 | 선택지 | 지원 모델 | 처리 위치 |
|---|---|---|---|
| **PTU + 한국 내 처리** | **`ProvisionedManaged`**(Regional) | 폭넓음 | Korea Central 고정 |
| PTU + 위치 무관 | `GlobalProvisionedManaged` | 전 모델 | 전 세계 |
| 토큰 과금 + APAC 내 | `DataZoneStandard` | ⚠️ **gpt-5.2 이상만** | APAC 내 |
| 토큰 과금 + 한국 내 | `Standard` | 폭넓음 | Korea Central |
| **PTU + APAC 존** | ❌ **불가** | — | — |

> ⚠️ 한국에서 **"PTU + 데이터 상주"** 가 필요하면 답은 Data Zone이 아니라 **`Regional Provisioned`** 입니다. 비싼 최소 PTU와 리전별 예약을 감수해야 하며 **우회로가 없습니다.**

### Standard 계열

- 상주 요건이 허용하면 **Global Standard 1순위**, 지리 경계 필요 시 **Data Zone Standard 2순위**
- ⚠️ **Provisioned → Standard로 Failover하는 순간 지연 SLA 밖으로 나갑니다**

## 4. Spillover — 정확히 무엇인가

### 재시도 주체는 **AOAI 서비스**(서버 측)

```
Client ──1건──▶ PTU ──(429/400/500/503)──▶ [서비스가 자동 전달] ──▶ 표준 배포 ──▶ 200
```

- HTTP 요청은 **처음부터 끝까지 1건**. 클라이언트 재시도 카운트에 안 잡힘
- 성공하면 **클라이언트는 429를 받지 않음**

### 트리거는 429만이 아닙니다

| 코드 | 상황 |
|---|---|
| 429 | PTU 소진 |
| **400** | **긴 컨텍스트** (PTU의 컨텍스트 상한 초과) — PTU 증설로 해결 안 됨 |
| 500/503 | 서버 오류 |

### 제약은 "동일 리전"이 아니라 **"동일 리소스 = 동일 엔드포인트"**

- Global PTU ↔ Global Standard면 **양쪽 다 글로벌 라우팅** → 리전 용량 편중은 상당 부분 흡수 ✅
- 그러나 **같은 엔드포인트를 공유** → 그 리전 장애 시 **둘 다 도달 불가** ❌

### 🚨 대상 유형 페어링 — 컴플라이언스 함정

문서상 대상 SKU 제한은 **없습니다**. 그래서 잘못 고르기 쉽습니다.

| PTU 유형 | 권장 대상 | 잘못 고르면 |
|---|---|---|
| Global Provisioned | **Global Standard** | 리전 Standard → 단일 리전 쿼터에 묶여 이점 상실 |
| Data Zone Provisioned | **Data Zone Standard**(동일 존) | 🚨 **Global Standard → 오버플로가 데이터 존 밖에서 처리** |

> **Data Zone PTU → Global Standard 조합은 오류가 나지 않습니다.** 감사 시점에야 발견됩니다.

### 표준 배포도 실패하면?

**클라이언트는 "마지막 백엔드"의 응답을 그대로 받습니다.**

| PTU | 표준 | 클라이언트 | `x-ms-spillover-error` |
|---|---|---|---|
| 429 | 200 | **200** ✅ | 429 |
| 429 | 429 | **429** | 429 |
| **400** | 429 | **429** | **400** ← 원인과 다름 |

→ **Spillover가 있어도 클라이언트 재시도 로직은 유지**해야 합니다.

### 🔴 관측 함정 — PTU에 429가 안 찍힙니다

Spillover된 요청은 **표준 배포 쪽에 `IsSpillover=True` + 200**으로 기록됩니다.

> 문서 예시: PTU 배포 200=**46**, 표준 배포(IsSpillover) 200=**954**

**429 카운트만 보면 954건이 넘쳤는데도 "포화 없음"으로 오판합니다.**
→ `IsSpillover` 또는 `Provisioned Utilization V2`로 판단하세요.

### 대가: 지연 + 과금 전환

- 실패한 PTU 시도 + 표준 처리가 **한 요청에 누적**
- **PTU 시간당 → 표준 토큰 단가**로 과금 전환 → Spillover 급증 = 비용 급증

## 5. 클라이언트 복원력

### `Retry-After` 처리 (가장 중요)

AOAI는 **1일 단위 같은 큰 `Retry-After`** 를 줄 수 있습니다.

```
if 429:
    if Retry-After <= 상한(예: 30초):  대기 후 재시도
    else:                              대기하지 말고 즉시 다른 백엔드로 전환
```

- 그대로 대기 → 서비스 정지
- 무시하고 즉시 재시도 → **스로틀 증폭**

### 재시도 대상

| 재시도 O | 재시도 X |
|---|---|
| 429, 500/502/503/504, 408 | 400, 401, 403, 404, **499** |

### 타임아웃 정합성

```
클라이언트 타임아웃 ≥ (시도 횟수 × 게이트웨이 timeout) + 재시도 간격 합
```

**안쪽이 먼저 실패해야** 바깥이 그 실패를 처리할 수 있습니다. 역전되면 고아 작업·부하 증폭·진단 불가·서킷 브레이커 무력화가 동시에 발생합니다.

## 6. APIM AI Gateway

### 필수 3종

| 항목 | 설정 | 없으면 |
|---|---|---|
| **서킷 브레이커** | 429 + 5xx, `acceptRetryAfter: true` | 죽은 백엔드로 계속 전송 |
| **우선순위 풀** | `priority` 1/2/3 | — |
| **Managed Identity** | **`Cognitive Services OpenAI User`** | 키 유출 위험 |

> ⚠️ **하위 우선순위 그룹은 상위 백엔드가 전부 서킷 브레이커로 차단됐을 때만 사용**됩니다.
> **서킷 브레이커 없는 우선순위 풀은 무의미합니다.**

> ⚠️ APIM 공식 문서는 `Cognitive Services User`를 안내하지만, 이 역할은 **계정 키 조회 권한(`listkeys`)** 을 포함합니다. **최소 권한은 `Cognitive Services OpenAI User`** 입니다.

### `forward-request` 설정

```xml
<forward-request timeout="60"
                 buffer-request-body="true"    <!-- 재시도에 필수 -->
                 buffer-response="false" />    <!-- SSE 스트리밍에 필수 -->
```

| 속성 | 주의 |
|---|---|
| `timeout` | **응답 헤더까지의 시간** · **시도 1회당** 적용 · 240초 초과는 무시될 수 있음 |
| `buffer-response` | 기본 `true`는 **8KB 버퍼링** → 스트리밍 무력화 |

> 스트리밍에서는 `timeout`이 **TTFT만 제한**하고 전체 생성 시간은 제한하지 않습니다.

### 기타
- `llm-token-limit` — 테넌트별 토큰 쿼터로 노이지 네이버 차단
- 시맨틱 캐싱 — HA 관점에서는 **429 자체를 예방**하는 수단
- 짧은 재시도 + 명확한 서킷 브레이커 (재시도 과다는 서킷 브레이커를 방해)

## 7. 멀티 리전 · 권장 아키텍처

### 엔터프라이즈 PTU 풀 패턴

조직 전체가 공유하는 **하나의 큰 PTU 풀**을 두고 게이트웨이가 앱별로 분배합니다. 일종의 **"우리 조직 전용 Standard 배포"** 로, 공용 Standard가 혼잡해도 전용 용량이 보장되고(노이지 네이버 차단), 워크로드를 합치면 스파이크가 평탄해져 **PTU 활용률이 올라갑니다.**

```
App → APIM ─┬─[P1] 워크로드 전용 PTU   (Region A)
            ├─[P2] 엔터프라이즈 PTU 풀  (Region B)
            └─[P3] Standard            (Region C)
```

- P1→P2 단계에서도 **PTU 엔드포인트가 처리** → 지연 SLA 유지
- P3(Standard) 도달 시 **SLA가 best-effort로 하락** → 성능 저하 모드 발동 지점

> ⚠️ 풀의 배포 유형: 상주 요건이 없으면 **Global Provisioned**가 가장 유연(예약 리전 무관). US/EU 경계가 필요하면 Data Zone Provisioned. **APAC은 Data Zone PTU가 없어 Regional Provisioned만 가능**합니다.

### 🔑 리전 반(反)상관 원칙

**PTU와 그 백업을 같은 리전에 두면 리전 장애 시 둘 다 사라집니다.**

- 워크로드 PTU ↔ 엔터프라이즈 PTU 풀 → 서로 다른 리전
- 엔터프라이즈 PTU 풀 ↔ 주력 Standard → 서로 다른 리전

### 리소스 배치

- **동일 구독에 2개 리소스**(주/보조 리전) — 쿼터는 **구독+리전** 단위라 상호 잠식 없음
- 각 배포에 **가용 쿼터를 전부 할당**(분할보다 처리량 높음)
- 💡 **리소스 리전 ≠ 앱 리전 가능** — 용량 있는 리전에 리소스를 만들고 **앱 근처에 Private Endpoint** 배치
- 구독 쿼터 소진 시 **새 구독 추가** 후 게이트웨이 뒤에 배치

| 전략 | RTO | RPO |
|---|---|---|
| Hot/Hot | 분 | ~0 |
| Hot/Warm | 30분~2시간 | 분~시간 |
| Hot/Cold | 2~8시간 | 시간 |

> 💡 **가장 위험한 건 "한 번도 트래픽이 흐른 적 없는 Failover 경로"** 입니다. 상시 1~5% 카나리 트래픽으로 살려두세요.

## 8. 용량 · 쿼터 · 예약

### 쿼터는 **(구독 × 리전 × 배포 유형)** 단위

- Global / Data Zone / Regional은 **완전히 별개 풀**
- Failover에서 **유형이 바뀌면 그 유형의 쿼터를 따로 확보**해야 함

### 예약(Reservation)

| 특성 | HA 영향 |
|---|---|
| **유형별 별개 구매** | Failover로 유형 바뀌면 **할인 미적용** |
| **Global 예약은 리전 무관** | ✅ 단일 예약으로 **여러 리전 커버** → 다중 리전 HA에 최적 |
| Data Zone/Regional은 **리전 일치 필요** | 리전마다 별도 예약 |
| **예약 ≠ 용량 보장** | **배포로 용량 확인 후** 예약 구매 |

### 반드시 계산할 시나리오

| 시나리오 | 질문 |
|---|---|
| 정상 | Primary가 100% 처리하는가 |
| Primary 포화 | Spillover가 피크 초과분을 흡수하는가 |
| **Primary 상실** | **Secondary가 평상시 트래픽 100%를 받는가** ← 핵심 |

## 9. 모델 수명주기 · 성능 저하

### 수명주기 (인프라 이중화로 못 막음)

- 프로덕션은 **버전 고정** (자동 업그레이드 금지)
- 분기별 **은퇴 일정 점검**
- 리전 간 **버전 동기화** (Failover 후 결과가 달라지면 안 됨)

### 우아한 성능 저하

| 단계 | 전략 |
|---|---|
| 1 | 다른 배포/리전 |
| 2 | **경량 모델 다운그레이드** |
| 3 | 시맨틱 캐시 응답 |
| 4 | 규칙 기반/검색 결과만 |
| 5 | 명시적 안내 |

**전면 포화 시 "느린 실패"보다 "빠른 대체 응답"이 낫습니다.**

## 10. 검증

> **테스트하지 않은 Failover는 없는 것과 같습니다.**

| 훈련 | 확인 |
|---|---|
| PTU 포화 유도 | Spillover 발생(`IsSpillover`), 사용자 실패율 |
| Primary 엔드포인트 차단 | 서킷 브레이커 trip 시간, Failover 소요 시간 |
| 큰 `Retry-After` 모의 | 대기하지 않고 전환하는가 |
| 게이트웨이 리전 차단 | Front Door 우회 |

**측정**: MTTD · Failover 소요 시간 · **실효 성공률**(재시도·Failover 포함) · 성능 저하 지속 시간

## 11. HA 성숙도 레벨

| Level | 구성 | 견디는 장애 |
|---|---|---|
| **L0** | 단일 배포 · 재시도 없음 | 없음 |
| **L1** | + 백오프, `Retry-After` 준수, 타임아웃 정합성 | 순간 429/5xx |
| **L2** | + **Spillover** | 용량 포화 |
| **L3** | + **APIM 우선순위 풀 + 서킷 브레이커** + **리전 반상관** | + **엔드포인트 장애** |
| **L4** | + Front Door 다중 APIM, **3단 PTU 체인**, 성능 저하 모드 | + 게이트웨이·구독 장애 |

## 12. 최종 체크리스트

**설계**
- [ ] Global/Data Zone/Regional 중 **의식적으로 선택**하고 근거 문서화
- [ ] **PTU · 엔터프라이즈 풀 · Standard가 서로 다른 리전**(반상관)
- [ ] "Global이니까 리전 장애에 안전"이라고 가정하지 않음

**구현**
- [ ] `Retry-After` 해석 + 과도한 값이면 **경로 전환**
- [ ] **Spillover가 있어도 클라이언트 재시도 유지**
- [ ] Spillover 대상이 **PTU 유형과 페어링**(특히 Data Zone)
- [ ] 타임아웃 총 예산 = (시도 × timeout) + 간격 ≤ 클라이언트 타임아웃
- [ ] 스트리밍 시 **`buffer-response="false"`**
- [ ] **모든 백엔드에 서킷 브레이커**(429 + `Retry-After` 수용)
- [ ] Managed Identity = **`Cognitive Services OpenAI User`**
- [ ] `x-ms-spillover-*` 헤더 로깅

**운영**
- [ ] Failover 리전이 **평상시 트래픽 100%** 감당
- [ ] **쿼터가 아니라 용량(capacity)** 정기 확인
- [ ] **배포 유형별 쿼터** 각각 확보 · 예약이 Failover 대상을 커버
- [ ] **PTU 축소·재확대 운영 금지**
- [ ] PTU 포화를 **`IsSpillover`/사용률**로 판단(429 아님)
- [ ] **표준 배포의 429**에 알림(실사용자 영향 지표)
- [ ] 분기 1회 Failover 훈련

## 자주 하는 실수 Top 10

1. **Spillover만 구성하고 "HA 완료"** — 엔드포인트 장애에 무력
2. **"Global이니까 리전 장애에 안전"** — 처리만 글로벌, 엔드포인트는 리전 고정
3. **PTU를 하나의 유형으로 취급** — 최소 PTU·쿼터 풀·예약·Spillover 권장이 모두 다름
4. **APAC에서 Data Zone Provisioned를 계획** — 제공되지 않음. 개념 문서가 아니라 **가용성 표**로 확인할 것
5. **PTU와 백업을 같은 리전에 배치** — 동시 소실
6. 🚨 **Data Zone PTU → Global Standard Spillover** — 데이터 존 이탈, 오류 없이 감사 때 발견
7. **PTU 포화를 429로 판단** — Spillover 시 PTU에 429가 안 찍힘
8. **쿼터만 확보하고 용량 미확인** — 배포 자체가 실패
9. **긴 `Retry-After`를 그대로 대기 / 무시하고 즉시 재시도** — 정지 또는 증폭
10. **서킷 브레이커 없이 우선순위 풀만 구성** — 하위 우선순위가 절대 사용 안 됨
11. **한 번도 트래픽이 흐른 적 없는 Failover 경로** — 장애 때 처음 실행되어 실패
